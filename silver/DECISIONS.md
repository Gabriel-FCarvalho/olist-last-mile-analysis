# Silver Layer — Decisions & Findings

## Context

This document records the decisions made, transformations applied, and validations performed during the Silver layer setup of the `olist-last-mile-analysis` project.

The Silver layer reads from `workspace.bronze` and delivers cleaned, typed, and standardised tables ready for analysis.

---

## 1. Scope Change — Business Questions

The project was originally scoped around four business questions. After review, the scope was reduced to three questions with a clearer logical progression:

1. **Where does delay occur in the delivery cycle?** — diagnosis
2. **What is the impact of delay on customer satisfaction?** — consequence
3. **Which regions and routes concentrate the worst results?** — direction for action

This structure tells a complete story: identify the problem, measure the impact, point to where to act. A financial analysis was considered but ruled out — the Olist dataset does not contain financial data, and drawing financial conclusions without that data would be speculation.

## 2. Transformations Applied

### 2.1 orders

**Source:** `workspace.bronze.orders`
**Target:** `workspace.silver.orders`

Two new columns were added:

| Column | Type | Logic |
|---|---|---|
| `is_delivered` | boolean | `true` when `order_delivered_customer_date IS NOT NULL`, `false` otherwise |
| `delay_days` | integer | `DATEDIFF(order_delivered_customer_date, order_estimated_delivery_date)` — calculated only when `is_delivered = true`, `NULL` otherwise |

**Design decision:** null delivery dates are not dropped. They are made explicit through the `is_delivered` flag. Dropping them would hide the fact that 2,965 orders were never delivered, which is directly relevant to the last-mile analysis.

A positive `delay_days` value means the order arrived after the estimated date. Negative means it arrived early.

**Validation results:**

| Metric | Value |
|---|---|
| Total rows | 99,441 |
| Delivered | 96,476 |
| Not delivered | 2,965 |
| Null delay_days | 2,965 |
| Min delay_days | -147 |
| Max delay_days | 188 |

### 2.2 order_reviews

**Source:** `workspace.bronze.order_reviews`
**Target:** `workspace.silver.order_reviews`

Two transformations applied:

- `review_score` cast from `string` to `integer`
- 26 records with invalid `review_score` values excluded via `WHERE review_score IN ('1','2','3','4','5')`

**Why filter before casting:** the Bronze table contains timestamps and text fragments in the `review_score` column due to the multiLine parsing issue documented in the Bronze DECISIONS.md. Attempting to cast those values directly would produce errors or silent nulls. Filtering first ensures only valid values reach the cast.

**Validation results:**

| Metric | Value |
|---|---|
| Total rows | 99,223 |
| score_min | 1 |
| score_max | 5 |
| Null review_score | 0 |

### 2.3 products

**Source:** `workspace.bronze.products`
**Target:** `workspace.silver.products`

Two column renames applied to correct typos present in the original Olist dataset:

| Bronze name | Silver name |
|---|---|
| `product_name_lenght` | `product_name_length` |
| `product_description_lenght` | `product_description_length` |

The Bronze table preserves the original naming. The Silver table delivers the corrected version.

---

### 2.4 geolocation

**Source:** `workspace.bronze.geolocation`
**Target:** `workspace.silver.geolocation`

The Bronze table contains 1,000,163 rows with multiple coordinate entries per zip code. A direct JOIN with `orders` using this table would produce duplicate rows and inflate results.

Aggregation was applied using `GROUP BY geolocation_zip_code_prefix`:

| Column | Aggregation | Reason |
|---|---|---|
| `geolocation_lat` | `AVG` | Central coordinate for the zip code area |
| `geolocation_lng` | `AVG` | Central coordinate for the zip code area |
| `geolocation_city` | `MAX` | All entries for the same zip code share the same city — MAX satisfies SQL aggregation rules |
| `geolocation_state` | `MAX` | Same reasoning as city |

**Validation results:**

| Metric | Value |
|---|---|
| Total rows | 19,015 |
| Distinct zip codes | 19,015 |
| Null lat | 0 |
| Null lng | 0 |

One row per zip code confirmed.

---

### 2.5 customers, sellers, order_items, order_payments, product_category_translation

No type corrections or business logic applied. The only transformation was excluding the `_rescued_data` column generated by Databricks during the Bronze load.

---

## 3. _rescued_data Removal

The `_rescued_data` column is generated automatically by Databricks `read_files()` to capture data that does not fit the inferred schema. It appears in all Bronze tables and carries no analytical value.

It was removed from all Silver tables by simply not including it in the `SELECT` statement. No explicit `DROP` command is needed — columns excluded from the SELECT are not written to the new table.
